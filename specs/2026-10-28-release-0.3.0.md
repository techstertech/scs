# SCS 0.3.0 release

## Approved outcome

The user authorized restarting SCS, manually testing the four review features,
and releasing only after successful checks. Publish an additive minor release
through the existing GitHub workflow. Preserve settings, repository registrations,
index state, Cortex, and active terminal sessions.

The checkout lacked the published 0.2.4 trusted-host fix and 0.2.5 nested-repository
fixes. Merge `4836cce` preserves both before candidate verification.

## Acceptance criteria

1. Supported cooperative lifecycle replaces the daemon with the candidate and
   reports readiness. Configuration and existing project identities are preserved.
2. A fresh stdio MCP client exposes the new optional inputs and investigation
   result while retaining exactly five tools.
3. A disposable repository, indexed through the live daemon, returns changed
   symbols, supported direct/indirect dependency paths, and relevant test candidates.
4. Live queries distinguish active/superseded contracts, resolve unique anchors,
   preserve ambiguity, and distinguish assessed, empty, partial, and unassessed work.
   Invalid ranges and escaping paths are rejected. Fixture resources are removed.
5. Version identity, required local checks, and hosted macOS/Linux CI pass before
   tagging. The signed annotated tag identifies the verified commit on main.
6. Release assets have valid checksums and GitHub provenance. The supported public
   installer activates the published wheel, and installed-wheel MCP checks pass
   outside the checkout with existing configuration and registrations preserved.

## Verification and release gates

Use candidate `scs daemon restart`, fresh stdio MCP sessions, procedural source
fixtures, and real public tools. Preserve baseline configuration/catalog fingerprints.
Use the existing native parser/index rather than injecting graph evidence.
Run `just verify`, release version checks, and the existing balanced relevance
suite. Treat failed behavioral checks as release blockers; fix and retest first.
Require hosted CI success before pushing the release tag. Verify both platform
wheels through hosted installation smoke tests, then checksum/provenance checks.

## Recovery and boundaries

No graph migration or production dependency change is planned. Use the installed
0.2.3 executable for pre-publication rollback if candidate activation fails.
Published 0.2.5 provides rollback after installation. Never replace published
assets; corrections require a new release. Do not restart Cortex or its terminal
runtime. Temporary fixture index deletion is limited to the created fixture root.
